# 本地交付：启动、配置与凭据

[English](README.md) · **简体中文**

课程 ID：`local-delivery`。课号按目录顺序计算，只在网页上显示；文件里提到课程一律写课名或课程 ID。

状态：`planned`。实现、离线测试和中英文内容已经写完；离线测试真实启动子进程，但本课还没有经过网页上的验收运行，网页上仍然置灰。

## 本课要解决的问题

前面的课都在你自己的机器上跑：依赖装好了，环境变量是现成的。把工具交给别人，缺的东西才一件件露出来：终端安静了三秒，进程在跑吗？卡在哪一步？日志里有什么？更糟的是，贴出来的日志里夹着 API Key。

本课不调用模型，也不需要密钥。它把课程目录里的一个小型本地服务 `notes_app`（笔记应用）真的启动起来，逐项做交付检查，检查读的是真实子进程的退出码、端口、日志和文件：

- 配置分三层（默认值 < 配置文件 < 环境变量），每个值带着来源；缺必填项、配置文件里放凭据、写错键，都在监听之前被拒绝，一次点名全部问题，错误里没有任何值；
- 存活探针 `/health` 和就绪探针 `/ready` 分开回答；卡住、不就绪、端口被占用，都在上限处如实报告；
- 停止先 `SIGTERM`、再杀整个进程组；只杀主进程会留下后台工作进程（孤儿进程）；
- 日志每行一个 JSON；凭据只报“已设置”和来源；带缺陷的版本把整份配置写进日志时，扫描能定位到行号和设置项，展示的内容已脱敏；
- 整组被杀后数据完整、重启后恢复、重发的写入不重复；不兼容的新配置在监听前被拒绝，备份放回去之后服务恢复。

## 文件导览

| 文件 | 内容 |
| --- | --- |
| `notes_app.py` | 被检查的小服务：标准库 `http.server`，`/health`、`/ready`、`/config`、`/notes`，JSON 日志，后台工作进程，SIGTERM 收尾；`--fault` 注入故障（卡住不监听、预热不结束、把配置写进日志），只服务检查 |
| `settings.py` | 三层配置：默认值 < 配置文件 < 环境变量，收集全部问题，凭据只从环境变量读；应用和检查共用 |
| `notes_store.py` | 数据文件：先写临时文件再改名，`op_id` 让重发的写入只生效一次 |
| `launcher.py` | 运行器一侧：白名单环境、拉起子进程、等端口文件、探测、先 SIGTERM 再杀进程组、进程是否真的消失 |
| `logscan.py` | 读回日志：是否结构化、生命周期事件是否齐全、有没有凭据值、脱敏 |
| `runtime.py` | 运行器：四个场景，每一步一份 `lesson.report`，以及 `lesson.process`、`lesson.probe`、`lesson.start_failed` 事件 |
| `locales/zh_CN.py`、`locales/en.py` | 运行时文本：报告标题、检查的标签与说明、指标标签、答案 |
| `locales/__init__.py` | 消息目录的字段定义 |
| `test_lesson.py` | 行为测试：配置规则、数据文件、日志扫描、真实子进程的启停、四个场景（两种运行语言）、凭据不出现在任何事件里、取消后不残留进程、输入校验 |
| `content.json`、`content.en.json` | 教学内容与英文译文层 |
| `lesson.json`、`lesson.en.json` | 实现清单（练习、运行器）与英文译文层 |

本课没有 `fixtures.py`：它不调用模型，不需要确定性的模型回复；检查用的都是真实进程。

## 怎么运行

离线测试（不需要密钥，也不联网；会真实启动子进程，约 20 秒）：

```bash
.venv/bin/python -m unittest lessons.lesson_local_delivery.test_lesson -v
```

课程开放后，在网页实验台选练习即可运行，不需要先配置模型。运行时每个练习会在临时目录里拉起和停掉若干个子进程，结束后目录和进程都会清理。

本课练习里的“密钥”是每次运行现编的假密钥（`sk-demo-` 加随机字符），不会读取你真实的 Key，也不会出现在任何事件、日志展示或答案里。

## 练习

| 练习 | 场景 | 真实子进程 | 约耗时 |
| --- | --- | --- | --- |
| 配置分层：缺失、来源与凭据（`config-layers`） | 预测三层解析、真实子进程回报；什么都不配；配置文件里放凭据和写错的键 | 3 个，其中两个在监听前就退出 | 约 1 秒 |
| 启动、就绪与停止（`startup-probe`） | 正常启动与停止；卡住；存活但不就绪；端口被占用；只杀主进程与杀整个进程组 | 5 个 | 约 5 秒 |
| 结构化日志与凭据泄漏（`logs-and-secrets`） | 正常运行的日志；带缺陷的版本把配置写进日志 | 2 个 | 约 1.5 秒 |
| 崩溃重启、重发写入与配置回退（`restart-rollback`） | 写入、备份、杀整个进程组；重启、重发；读不了的新配置；备份放回 | 4 个 | 约 2 秒 |

可调的输入（实验台的参数面板）：

- `scenario`：选哪个场景，四个练习各自固定；
- `startup_timeout_ms`（默认 1200）：等待监听的上限；调得太小，正常启动也会超时；
- `ready_timeout_ms`（默认 1200）：监听之后等 `/ready` 返回 200 的上限；比预热时间短时，正常启动会被如实报告为不就绪；
- `warmup_ms`（默认 400）：应用模拟的依赖预热时长。

## 实验看什么

1. **配置、凭据与日志**（`config-layers` 和 `logs-and-secrets`）
   - 报告里三层各贡献了几个设置项，`model` 一行写着文件和环境变量各是什么、最终取哪个；
   - 第 2 轮、第 3 轮的 `lesson.start_failed`：`problems` 里只有设置项的名字和问题代码，退出码是 2；
   - 日志那一组：生命周期事件齐全；带缺陷的那次，“日志里没有凭据的值”不通过，展示的行里是 `[REDACTED:api_key]`，交付闸门拦下。
2. **启动、就绪与停止**（`startup-probe`）
   - 探针时间线：`/health` 立刻 200，`/ready` 预热期间 503，之后 200；
   - 第 2 轮 `lesson.start_failed` 的 `alive`：超时时进程还活着，是卡住；
   - 第 3 轮 `not_ready` 的 `limit_ms`；第 4 轮退出码 3 与 `EADDRINUSE`；
   - 第 5 轮 `leader_killed` 的 `orphans`：只杀主进程后残留 1 个进程，按进程组回收后为 0。
3. **崩溃重启与配置回退**（`restart-rollback`）
   - 整组被杀后重启，读到 2 条笔记；重发 `op-2` 不重复，新的 `op-3` 写入；
   - 读不了的新配置：`settings_version` 不支持、`model_id` 是未知键、缺 `model`；
   - 回退之后两个文件的摘要和之前一致。

## 本课的边界

- 只覆盖本机一个小服务。不涉及云端部署、多用户、容器编排。
- 不探测模型和 MCP。真实模型是否可用，要在模型连接设置里用真实请求验证；“已配置”不等于“已验证”，没验证过的服务商不能标成可用。
- 假密钥证明的是检查的逻辑，不证明你真实的密钥管理做对了。日志扫描只能找到已知的、原样出现的值。
- 回退只涉及配置文件；数据格式迁移的回退没有演示。
- 杀的是进程组，不是断电；断电后磁盘缓存能否保证，取决于文件系统和硬件。
